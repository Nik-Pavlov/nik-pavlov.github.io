1 · Goal

Spend CPU to save memory

  • Every LogoBlob SST keeps its index in RAM for its lifetime; it grows linearly with the data a VDisk holds.
  • The on-disk record is 44 B (24 B key + 20 B memrec). On main the in-memory index takes 43.9 B/record on production data: as much as the disk format.
  • This PR: a two-level fix as the default form, and the compact Packed form behind a feature flag, chosen per SST when it is loaded or written by compaction.
  • Disk format and everything above the segment stay unchanged.
Index bytes per record, all 5 snapshots

Totals: main 4,596 MiB, two-level fix 3,353 MiB, Packed 1,144 MiB for 109.7 M records. 5 production index snapshots of block-storage clusters (block-4-2), 4,212 SSTs, 109.7 M records; memrecs synthesised.

2 · The problem on main

The shared high part holds Step >> 8, which changes every few records

Step of 40 consecutive records of one tablet / channel / generation group in the largest SST of one snapshot. Block-storage tablets advance Step per commit; each shaded band is one value of Step >> 8.

A new 20-byte high record starts whenever Step >> 8 changes: here every 1.8 records, over the whole SST every 1.05, over all snapshots every 1.25. So 28 + 20 / 1.25 = 44 B per record (measured 43.9): as big as the flat on-disk record.

3 · The fix

Step moves into the low part: one high record per (tablet, channel, generation)

Memory 43.9 → 32.05 B/record (-27%), 32.0-32.1 on every snapshot; 472 records per high record on average. TRecLow is 32 B and 32-byte aligned. Counter-example: on the load actor's keys (end-to-end test: few tablets, one channel, consecutive Steps) main shares its high parts well and takes 28.0 B per item against 32.0.

4 · Packed

Fixed-width columns: O(1) access by position

Keep the two-level high part; store each low field as a column of fixed-width bit fields. Field c of record i sits at a computable bit position: no sequential decoding, the iterator is the two-level one with an index instead of a pointer.

Dict

PartCrc, BlobSize, Ingress, TypeId, Size: few distinct values per SST; store the index into the SST's sorted distinct values.

BlobSize 9.2 bits (raw 26), Ingress 12.0 (raw 64), PartCrc 2.3 (raw 6), dictionaries included.

Frame

Step, Cookie, Offset: change little between neighbours; per 32 records a base (the minimum) and a bit width, each value stored as value - base.

Step 17.7 bits (raw 32; as a Dict 78), Cookie 6.0 (raw 24), frame headers included.

Bits per record over all 5 snapshots. Memrec fields (TypeId, Offset, Size) are synthesised in the snapshots, so their survey is left out.

Frame of 64 instead of 32 saves another 1.4%.

4 · Packed

Before and after: twelve records in Packed

Records 4,044 ... 4,055 of the largest SST of one snapshot. Each column holds one field of every record; record i of a column sits at its start + i x width.

Computed as TPackedLogoBlobSstIndex::PackDict / PackFrame do: Dict index = position in the SST's sorted distinct values, width = bits of (count - 1); Frame = 32 records by position, base = minimum, width = bits of (max - min). The Step frame jumps by ~0.6 M at its end, hence 20 bits (17.7 on average over all snapshots). Any record's value is one shift and mask away.

6 · How the index is used

Nothing above TLevelSegment knows the form

The policy comes from the EnableVDiskPackedSstIndex feature flag, latched at VDisk start (restart required). Switching it either way is safe: in-memory indexes are rebuilt from the unchanged on-disk records.

Build cost adds to VDisk startup and to compaction. Iterator cost shows in merges, reads and full scans.

7 · Operation-level benchmarks

A Get costs 0.9-1.1x main with Packed; a compaction step 2.0-2.1x

maintwo-level fixPacked
  • A Get seeks ~21 SSTs of one VDisk: level 0 plus every level whose key range holds the key.

7 · Cache behaviour

Row layouts evict a neighbour's cache; Packed barely does

maintwo-level fixPacked
  • The row layouts stream 11.1-11.7 GB/s (two-level fix) to 14-15 GB/s (main) through the L3 and push out all of the neighbour's data: its loads take DRAM latency at every size.
  • Packed streams 0.5 GB/s: harmless up to 8 MiB, but its columns and dictionaries live in the L3 and cost a near-full neighbour +29% / +68%.
  • Mostly a rate effect: per second Packed moves ~28x fewer bytes than main.

Neighbour: random pointer chase over 8 / 12 / 14 MiB on another core sharing the 16 MiB L3, while the bench scans one snapshot cold; slowdown = neighbour ns per load vs idle, median of 3. Other load shared the L3 during part of the run.

The bench does nothing but decode, so the row layouts stream at their maximum rate: an upper bound for compaction, which does work per record.

9 · Decision

Proposal: merge with Packed off by default

two-level fix: the default form

-27% on the production snapshots (43.9 → 32.1 B/record), cold scans and Gets faster than main even behind the variant.

+14% on load-actor keys; hot Next 4.0 vs main's 2.6 ns with the variant.

Packed: behind EnableVDiskPackedSstIndex

-75% (10.9 B/record), Packed smaller than main in every SST; 2.3x smaller RSS end to end.

Costs ~18 ns per Next, 1.2-1.3x on cold seeks, 2.0-2.1x per merged record, 1.9x startup; a Get is 0.9-1.1x main.

Before enabling Packed by default
  1. Real memrecs: Packed is 5.8-10.9 B/record depending on them; a snapshot with real memrecs turns the range into one number.
  2. Production-like keys end to end: the load actor's keys favour main and over-compress for Packed.
  3. Startup and full sync of a full node: build time adds to restart; a full sync iterates the sender's whole index (~1.3 s per peer for 45 M records, two-level ~0.3 s).
  4. Dispatch: ~1 ns per Next and ~20% of a cold Get with two forms; choosing the form once per SST would remove both.
  5. Oversized SSTs: the packed stream uses 32-bit bit positions and aborts above ~23 M records in the worst case (default SSTs hold up to ~3 M); a fallback to two-level is not implemented.
